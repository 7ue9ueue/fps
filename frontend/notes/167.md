# #167: series: pow, sqrt on backend/series

2026-10-13, claude. Base `25e3095` (origin/main).

`fps::pow`, `fps::sqrt`, `fps::raw::pow` and `fps::raw::sqrt` now run the backend's kernels for the
dense part (#107, PR #166: lc-opt's power and sqrt on `ntt::Transform`), and the frontend keeps
what DESIGN.md asks beyond them: the leading zeros (x^(z e), x^k), u[0]^e and e mod P for pow, the
smaller root of u[0] for sqrt, `std::optional`, the errors, and the few-term recurrence where it
still wins. Deleted: pow as exp(e log(u / u[0])) (a scaling pass, log, a pass, exp, a pass), the
frontend's own Newton sqrt on `raw::mul` (and with it `detail::series::at` and series.hpp's include
of `fps/products.hpp`).

## Paths

`detail::series::power(u, e, c, out)` and `detail::series::sqrt(u, c, out)` (no scratch argument
now: they take this thread's scratch only on the recurrence path, so a dense call no longer grows
a 3 n-word scratch it never touches; `compositional_inverse`'s call changed with it). The kernel
reads all of u before it writes, but raw::pow and raw::sqrt keep "out apart from f": the API did
not change.

The zeros below x^(z e) (x^k for sqrt) are now written after the kernel call, so a dense u past
2^25 throws `std::length_error` before out is written (before: pow wrote u / u[0] first, sqrt
threw from inside a Newton step with out partly written). DESIGN.md's pow/sqrt paragraph and the
header say so.

Where the recurrence (t <= 16 terms past u[0]) beats the kernel, measured with a throwaway bench
(`detail::series::sparse_power` against `fps::series::pow`, `sqrt` on u = u[0] + t random terms at
indices 1 .. t, n = 2^lg, one round of 5 samples; not committed). Recurrence / kernel:

|---|---|---|---|---|

| pow t = 8, lg 5 / 10 / 14 / 22 | 0.77 / 0.62 / 0.58 / 0.37 | 0.77 / 0.54 / 0.47 / 0.26 | 0.75 / 0.65 / 0.69 / 0.43 | 0.89 / 0.45 / 0.37 / 0.24 |

The recurrence costs about a + b t per coefficient (a = 7.5-13 ns from 2^8 on, 13-21 at 2^5; b =
0.3-1.1 ns); the kernel's pow costs 14-70 ns per coefficient and its sqrt 5-25, growing with n
past the caches. So the bounds (`detail::series`, speed choices only, the same results either way):

- pow: the recurrence for t <= 8 at any n (0.20-0.89 of the kernel everywhere), and for t <= 16
  from 2^17 coefficients on (0.31-0.95).
- sqrt: the recurrence for t <= 4 up to 2^8 coefficients (0.56-0.92 everywhere) and from 2^18 on
  (0.54-0.88 on three targets; 1.26-1.40 on Zen 5 at 2^18, 0.98-1.12 at 2^22 and 2^23, whose
  kernel sqrt is fastest, 5-8 ns per coefficient). The kernel otherwise.
- Past 2^25 (the kernel's limit), both run the recurrence for any t <= 16 (n <= P), as before.

A faster recurrence, chosen per target in the kernel, is backend issue #171.

The 6-7% of sqrt/11 (n = 1024, 7-14 us) is the root of u[0]: `detail::mod_sqrt` is
Tonelli-Shanks with s = 23 (P - 1 = 119 2^23), 0.4-1.0 us on the Mac (M4) for 4 and for random
squares, and the gap is about 0.7 us on Zen 3 (a guess that it is all of it; a table or precomputed
constants would cut it, not tried: frontend speed work, and only n below about 2^12 sees it). From
n = 8192 on the API is within 1.2% of the kernel. pow/11's 0.9-1.4%: u[0]^e for a 64-bit e
(0.17-0.27 us on the Mac) and the result's allocation.

sqrt_sparse/14 (1 - x - x^2, n = 2^14) now runs the kernel: 0.63-0.93 of the old recurrence's time
on the three x86 targets, 1.14 on Neoverse V2, where the recurrence takes 0.88 of the kernel's
time at that size (the table above). One bound for every target cannot take both; #171 would choose per target.

Against lc-opt (backend/series/notes/107-r1.md, `compare_pow.cpp` on `lc-bench`, the kernels
alone, same run): pow 0.95-1.02 and sqrt 0.94-0.99 of lc-opt's time from 2^14 to 2^21 (1.00-1.02
and 0.97-0.99 from 2^17); 0.61-0.81 on `lc-zen5` and `lc-intel` (lc-opt is AVX2 there). The API
calls run within 1.2% of those kernels from 2^13 on (above), so pow and sqrt through the API are
at lc-opt's speed on Zen 3 (a chain of two same-run ratios, not one three-way run).

`compositional_inverse` runs `detail::series::power` on a dense series: now the kernel's pow
instead of log + exp. `kernel.py bench frontend --filter compositional --base 25e3095` on
`lc-bench`, 5 rounds: lg 11 / 14 / 18 0.991 / 1.015 / 0.980 (power projection dominates; the pow is
a few % of it).

## Tests

`frontend/test_pow_sqrt.cpp`: everything it tested (O(n^2) references on sizes 0 .. 1025 with
leading zeros, both paths, closed forms at 10^6, identities to 300001, threads, errors), plus:
the term counts around the new bounds (t = 0, 1, 2, 4, 5, 8, 9, 16, 17 at n = 17, 40, 256, 257,
258, 1000, so s of 255 .. 257 coefficients for sqrt); the long bounds (pow with 9, 12, 16 terms at
2^17 and sqrt with 1, 4, 5 terms at 2^18, with and without leading zeros: the result cut by one
coefficient equals the other path's, and f^2 = f f, g^2 = f); past 2^25 (a dense f throws
`std::length_error` with out untouched, zeros of x^(z e) and x^k too; not under ASan: (1 - x)^(P -
1) = all ones and sqrt((1 - x)^2) = 1 - x at 2^25 + 1 by the recurrence). Whole file: 1.2 s at -O2
and 1.3 s under ASan/UBSan on the Mac.

`kernel.py test frontend` passes (-O2 and ASan/UBSan) on the Mac (scalar, arm), `lc-amd` (scalar,
sse, avx2), `lc-intel-test` (avx512), `lc-zen5-test` (zen5), `lc-arm` (arm).
