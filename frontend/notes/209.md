# #209: algebra: factor on backend/factor

2026-10-15, claude. Base `5ec304b` (origin/main).

`fps::factor` (`include/fps/algebra.hpp`) is now one call into the backend's factorization,
`fps::factorization::factor(f)` (`backend/factor/factor.hpp`, #123 r1, PR #202: lc-opt's Yun and
Berlekamp), for deg f <= 2048. Past 2048 it keeps the frontend's own path (Yun, distinct-degree
split, Cantor and Zassenhaus), now `detail::algebra::factor_by_splitting`, unchanged, until the
backend has a path for large degrees (#201). Nothing became unused: `pow_mod`, `Random`, `split`
and `factor_square_free` all serve that path.

## The wrapper

- f = 0 throws `std::domain_error` before the kernel, so its `std::invalid_argument` never
  escapes; deg f >= P throws `std::domain_error` as before.
- f passed trimmed to deg f + 1 words. Each `Factor` (a `std::vector<u32>` and a `u32`) becomes a
  `Polynomial` and an `int`. Order and content are the kernel's, sorted as DESIGN.md says (degree,
  then coefficients from the constant term); the old path sorts the same way.

## Where the paths cross (why 2048, not 4096)

The issue asked for the kernel up to its limit, 4096, and for the crossover. The kernel is
O(m^3) per square-free part of degree m (Krylov rows and an elimination on m x m matrices); the
frontend's path is O(n^2 log n log P) (up to n/2 distinct-degree steps, each about 30 squarings
modulo a part). Same run, 1 round (`kernel.py bench frontend --rounds 1 --filter
'^factor(_irreducible)?@(kernel|frontend)/1[012]$'`), s per call, kernel / frontend:

| input, degree | Zen 3 (`lc-bench`) | Emerald Rapids (`lc-intel`) | Zen 5 (`lc-zen5`) | Neoverse V2 (`lc-arm`) |
|---|---|---|---|---|
| random, 2^10 | 0.140 / 0.362 | 0.135 / 0.333 | 0.047 / 0.210 | 0.208 / 0.488 |
| random, 2^11 | 1.20 / 0.98 | 1.22 / 0.92 | 0.32 / 0.54 | 1.86 / 1.38 |
| random, 2^12 | 16.9 / 6.3 | 11.2 / 6.2 | 5.6 / 3.3 | 20.6 / 9.1 |
| irreducible, 2^10 | 0.159 / 0.369 | 0.158 / 0.332 | 0.041 / 0.210 | 0.206 / 0.495 |
| irreducible, 2^11 | 1.10 / 1.43 | 1.23 / 1.34 | 0.32 / 0.78 | 1.82 / 2.01 |
| irreducible, 2^12 | 17.0 / 5.8 | 14.1 / 5.5 | 5.6 / 3.0 | 20.2 / 8.4 |

(Apple M4 Pro, clang: random 0.10 / 0.30, 1.04 / 0.88, 10.2 / 6.1; irreducible 0.09 / 0.31,
0.81 / 1.29, 8.9 / 5.6.) Irreducible is (x + 12345)^n - 3 (3 generates the units mod P, n a power
of two: irreducible by Lidl and Niederreiter, Theorem 3.75), the frontend path's worst case.

The kernel's time grows 7-9x per doubling from 2^10 to 2^11 and 9-17x from 2^11 to 2^12 (its
matrices leave the caches: backend/factor/notes/123-r1.md, Large degrees); the frontend path's
2.6-4x and 4-7x. Interpolating the ratio in log-log, they cross at degree about 1700-1800 for a
random f on Zen 3, Emerald Rapids and Neoverse V2, about 2900 on Zen 5, and about 2100-2400 for
the irreducible f on all but Zen 5 (past 2^11 there too). At 2^12 the kernel is 1.7-2.9x slower.

One threshold, deg f <= 2048 to the kernel: at 2^11 that costs a random f 1.23-1.36x against the
frontend path on Zen 3, Emerald Rapids and Neoverse V2 and gains 1.08-1.30x on the irreducible f
there, and 1.7-2.4x on Zen 5; a threshold below 2048 would swap those. Per-target thresholds were
not worth a second constant. #200 (the kernel past 1024: GEMM-like blocking) would move the
crossover up; then `kFactorKernelMax` should be measured again (comment on #200).

## Tests (`frontend/test_algebra.cpp`)

Everything it tested now runs the kernel (known irreducibles with multiplicities, random f of
sizes 1-33 and four kinds checked by Rabin's test and their product, x^4 + 1, 74 planted factors,
threads, errors). New, `test_factor_paths`: both paths on the same inputs give the same list:
random f of every size in `kSizes` (0 to 129) and four kinds (squares f^2 (x + 1) to size 33),
random f of degree 255, 256, 257 (the kernel's kept factorizer, `kKeepDegree` = 256) and 300; then
A^e B, A of degree 64 (32 linear factors, 8 quadratics, 4 cubics, a quartic), B of degree 63, 64,
65 (3 quintics and linear factors), for e = 31 (degrees 2047-2049, the switch) and e = 63 (4095-4097,
the kernel's own limit), with trailing zeros on one: `fps::factor`, `factor_by_splitting` and
(degree <= 4096) the kernel called directly all give the planted list. Small square-free parts
keep the kernel's cubic cost low there; a random f of degree 2048 would take seconds per call on
scalar and minutes under ASan. `test_algebra` on the Mac: 0.82 s user at -O2 (0.55 s before),
2.1 s with ASan/UBSan.

`kernel.py test frontend` passes (-O2 and ASan/UBSan) on the Mac (scalar, arm), `lc-amd`
(scalar, sse, avx2), `lc-intel-test` (avx512), `lc-zen5-test` (zen5), `lc-arm-test` (arm).

## Against lc-opt

lc-opt's factorization (`problems/polynomial/factorization_of_polynomials`) holds polynomials in
128 words, so degree <= 100; no case here reaches it past that. The backend round's same-run
numbers on `lc-bench` (backend/factor/notes/123-r1.md, Results; the kernel, which the API matches
within 1%): fps / lc-opt geomean 0.786 over 12 cases of degree 16-100, 0.634 (100 linear factors)
to 0.873 (random, degree 64).

## For the backend

- `backend/factor/bench.cpp`'s `<case>@frontend` cases (not gated) now time the kernel through
  the API for degree <= 2048; they can go, or call `fps::detail::algebra::factor_by_splitting`.
- The crossover above is on #200: the kernel loses to an O(n^2 log n) path from about degree 2^11.
