# #272: geometric: raw::dft and raw::idft into caller memory

2026-10-18, claude. Base: main 018ef8a. GCC 16.2 (pinned image), each target's flags.

## Built

`fps::raw::dft<P>(f, out)` (L = `out.size()`) and `fps::raw::idft<P>(values, out)` in
`include/fps/geometric.hpp`, beside `fps::dft` and `fps::idft`. They share one path with them
(`detail::geometric::dft_plan` / `idft_plan`: the root and the errors; `detail::geometric::dft` /
`idft`: the call): one `ntt::dft` / `ntt::idft` for L = 2^6 .. 2^23, the chirp otherwise, so
the API calls now go through the same code.

- Errors: the same as `fps::dft` / `fps::idft`, all before out is written (L not a divisor of
  P - 1: `std::domain_error`; the chirp's middle product past 2^25 words: `std::length_error`),
  plus `std::domain_error` for `out.size() != values.size()` in idft. No check that the values
  are below P, as `raw::to_values`: the issue's reason for the function (4-8% of idft at 2^20).
- Aliasing: out may overlap the input, for any L. ntt::dft and ntt::idft read their input before
  writing out (backend/ntt/dft.hpp); the chirp needs them apart, so on that path an overlapping
  input is first copied into a per-thread scratch (`detail::geometric::apart`, kept and reused,
  as the Raw functions' contract allows). One rule for all L seemed simpler for the user than
  "may overlap for powers of two from 2^6 to 2^23 only".
- DESIGN.md, Raw functions: the two signatures, their aliasing and what they leave out.

## Tests

`frontend/test_geometric.cpp`, `test_raw_dft`: against `fps::dft` / `fps::idft` (tested against
Horner and the folded f) for L in {0, 1, 2, 7, 8, 17, 32, 34, 56, 64, 119, 128, 1024, 1904, 4096,
2^17} (transform and chirp lengths) and n in {0, 1, L/2, L-1, L, L+1, 2L+3}: into other memory
filled with garbage, in place, and with out one word before and after the input in one buffer.
Errors: lengths that do not divide P - 1, out of the wrong size (longer and shorter), nothing
written; the length errors into a 17 2^21-word `MAP_NORESERVE` map that is never touched.
A mutation (`apart` never copying) fails 40 checks. Mac `arm` and `scalar`, `lc-amd` `avx2`,
`sse`, `scalar`, `lc-intel-test` `avx512`, `lc-zen5-test` `zen5`, `lc-arm-test` `arm`: all pass,
-O2 and ASan/UBSan. (`lc-zen5-test`, 4 cores and 14 GB shared with other agents' runs, first lost
the ASan build of `test_division.cpp` to the OOM killer; the rerun with `-j 4` passed all 30.)

## Speed

`frontend/bench_geometric.cpp`: `dft@kernel` and `idft@kernel` were still the chirp (written
before #267, which moved powers of two to ntt::dft); they now call `ntt::dft` / `ntt::idft` into
new unwritten memory, as the API case's result is. New cases, lg 10, 14, 18, 20: `raw_dft`,
`raw_idft` (into a buffer kept across calls) and `raw_dft@kernel`, `raw_idft@kernel` (the
kernel into a buffer kept the same way); dft and idft gain lg 20.

The sign at 2^14 follows the filter, not the code: base's dft/14 is 24263-24281 ns with the
chirp cases run first and 23076-23088 without; new's 22999-23061 and 24684-24693. Both binaries
switch between the same two levels, in opposite states. My guess: the heap's history sets the
result vector's address, and ntt::dft's permutation is sensitive to the alignment of its natural
side (backend/ntt/notes/138-r1.md: 16 bytes past a line against 64-byte aligned). The code path of
`fps::dft` / `fps::idft` is unchanged (the same plan, one call into ntt::dft / ntt::idft). Runs 1
and 4 hold the chirp cases too; their geomean is the one in the PR's Speed section.

## Found

- `fps::dft` and `fps::idft` at 2^14 on Zen 3 move by 5-7% with the heap's state (above), in base
  as in new: the API's result is a `std::vector` whose address malloc picks. If it is the
  alignment, a result allocated on a 64-byte boundary (`Polynomial` and the vector via an aligned
  allocator) would remove the swing and the slow level; a bench of the kernel into `out` at 16
  and 64 bytes past a line, at 2^14 and 2^20, would tell. Not measured at 2^20 (there glibc
  serves the vector from mmap, at a fixed 16 bytes past a page, so it cannot swing; whether that
  fixed state is the slow one is the open part), so a note, not an issue. Users who need the steady
  speed have `raw::dft` / `raw::idft` into their own aligned buffer.
