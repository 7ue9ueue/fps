# #191: fraction: [k] on backend/bostan_mori

2026-10-13, claude. Started on main `0d6a23e`.

`Fraction::operator[]` is now one call, `fps::bostan_mori::coefficient(p.span(), q.span(), k)`
(#114 r1, PR #187). The frontend's loop (two `f * g` per bit of k, `negate_odd`, `every_other`,
`cut`, fresh polynomials per step) is gone, and with it the include of `fps/modular.hpp`.

## What the frontend does

- Nothing but the call: the kernel cuts p and q to k + 1 words, drops p's zero top words, and
  handles an all-zero p (the old loop's `p.degree() < 0` exit). q[0] != 0 is still the
  constructor's check, so the kernel's own `std::domain_error` (empty q or q[0] = 0) cannot
  happen. `take(n)` is unchanged.
- Limits: past 2^23 words of values form the kernel falls back to its `products` variant
  (`ntt::multiply`, `std::length_error` past 2^25), as the old loop's `f * g` did. Not tested at
  that size (d = 2^22 would take seconds per call); the kernel's tests own it.
- Memory: the kernel keeps per-thread arrays for the thread's longest call (huge pages), so a
  [k] allocates only when it is longer than the thread's earlier ones. `test_threads` (4 threads,
  d = 3000 and Fibonacci) covers the per-thread state through the API.

## Tests (`frontend/test_fraction.cpp`)

- New `test_kernel_paths`: sizes s = kSchoolbookMax - 1, kSchoolbookMax, + 1, 2 kSchoolbookMax
  + 1, kSchoolbookCapacity (256) and 257 (the schoolbook/values crossover on each target, and the
  values form handing off to schoolbook once the cut fits), with p of s, s - 1 (q with few terms),
  2 s + 3 words, p mostly zero over a q of 9, and q of s words with only 3 nonzero (trailing
  zeros) against p with its upper half zero. Every k below 2 max(|p|, |q|) + 70 against the
  O(n^2) recurrence, and k = 2^32, 10^18, 2^64 - 1 against Kitamasa on q without trailing zeros.
  The existing tests (sizes 0 to 1025, huge k, partial fractions up to d = 2048, d = 2^15
  against take, closed forms, DESIGN.md's examples, threads, errors) are unchanged.
- Also run with `-DFPS_BOSTAN_MORI_SCHOOLBOOK_MAX=0`, `1` and `256` on the Mac (values form only;
  schoolbook up to its capacity): all pass. The first run crashed in the test itself
  (`kSchoolbookMax - 1` wrapped around for 0); the sizes now start from max(kSchoolbookMax, 2).
- Mac (M4, -O2): 0.5 s for the whole test.
- `kernel.py test frontend` passes on the Mac (scalar, arm), `lc-amd` (scalar, sse, avx2),
  `lc-intel-test` (avx512), `lc-zen5-test` (zen5), `lc-arm` (arm). My first VM runs collided
  with each other (two `vm.py` runs into the same folder: one wiped the tree under the other's
