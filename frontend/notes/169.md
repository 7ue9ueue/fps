# #169: composition: compose, compositional_inverse on backend/composition

2026-10-13, claude. Started on main `25e3095`, rebased onto `3fd62d5` (#172, which changed the
one `detail::series::power` call this pull request deletes).

`include/fps/composition.hpp` now runs the general path of `compose` and all of
`compositional_inverse` as one call into the backend's kernel (`backend/composition/
composition.hpp`, #105, PR #148: Kinoshita and Li with lc-opt's layout, on every target). The
frontend's own Kinoshita and Li (`Grid`, `pack`, `graeffe`, `lift`, `kinoshita_li`,
`power_projection`, the Lagrange step on `detail::series::power`, and the size estimates
`compose_longest`, `projection_longest`) is gone: the header went from 285 lines to 130.

## What stays in the frontend

- compose: g mod x^n constant (Horner, O(f.size())), linear (Taylor shift and scaling; the
  tuned shift is backend issue #124), and the Taylor shift by a = g[0] before the kernel, which
  reads g[0] as 0. The kernel's output goes into an unwritten `Polynomial` (no zero fill).
- compositional_inverse: the API's checks (f[0] = 0 for n >= 1, f[1] != 0 for n >= 2, n <= P:
  `std::domain_error`), which the kernel leaves to the caller. Then the kernel does everything,
  n = 0, 1, 2 included.
- Limits: both throw `std::length_error` past the kernel's `kMaxSize` = 2^23 (its transforms have
  4 bit_ceil(n) words), with "fps::compose" / "fps::compositional_inverse" in the message, before
  any work (compose before the Taylor shift). The old frontend stopped at 2^22 (its products
  passed the NTT's 2^25 from 2^22 + 1), so n = 2^22 + 1 .. 2^23 now run. The Taylor shift keeps
  its own 2^25 check.
- Memory: the kernel keeps its work per thread (header and DESIGN.md say how much: compose
  about 16 m (log2 m + 3) bytes, 3.3 GiB at n = 2^23).

DESIGN.md, Functions: one paragraph on compose's paths, the 2^23 limit and the memory (the old
text named the paths only in the signature comment).

## Tests (`frontend/test_composition.cpp`)

- Everything it tested; the length errors now at 2^23 + 1 (g[0] = 0 and g[0] != 0, so the check
  comes before the shift) and 2^24; the Taylor shift's error on the general path with
  f of 2^25 - 2^23 + 2 words at n = 2^23.
- `test_limits` (vector targets at -O2, skipped on scalar and under ASan as before): compose at
  n = 2^23 with f = 1 + y + y^2 and g[0] != 0 against 1 + g + g^2 (`fps::mul`), and
  compositional_inverse of x + x^2 at n = 2^23 (signed Catalan numbers), each in a thread of its
  own so the kernel's 3.3 GiB is freed on exit; the Taylor shift at 2^25 words as before. Mac
  (M4, -O2, arm): 13.8 s for the whole test, 4.2 GB peak RSS (5.1 GB with both parts on the
  main thread).
- Time on `lc-amd`'s scalar target: Horner's references were most of it (n products of n words
  for n up to 1025). Horner now checks compose up to n = 257; above it, f of n + 3 is checked by
  its split at a random k, F(g) = F_lo(g) + g^k F_hi(g) (each part through compose on its own f,
  `fps::pow` and `fps::mul`), and compositional_inverse's f(g) = g(f) = x through compose. The
  identities' third size went from 100003 to 30011 (m = 2^15; `test_limits` covers the deep
  levels on vector targets). `test_composition` on `lc-amd` scalar (GCC 15.2, user time, a
  loaded machine): main 28.2 s at -O2 and 158 s under ASan/UBSan; after the rewiring 16.9 s and
  104 s; with the cheaper references 7.1 s; with 30011 too, 4.4 s and 26.7 s.
- A mutation that sends f instead of the shifted F to the kernel fails 1275 checks.
- `kernel.py test frontend` passes (-O2 and ASan/UBSan) on the Mac (scalar, arm), `lc-amd`
  (scalar, sse, avx2), `lc-intel-test` (avx512), `lc-zen5-test` (zen5), `lc-arm` (arm), on the
  rebased branch. One sse ASan run printed LeakSanitizer's "Unable to get registers from thread"
  in `test_products` and passed (seen before, #147).

## Against lc-opt

From the kernel's same-run comparison (`backend/composition/notes.md`, #105, `lc-bench`, n =
2^(lg-1)): fps / lc-opt at lg 11 / 14 / 18 is 1.41 / 1.44 / 1.44 for compose and 1.39 / 1.46 /
1.48 for compositional_inverse (fps 42.4 ms against lc-opt's 29.5 ms for compose at lg 18; here
the API on the same machine: 42.5 ms with g[0] = 0). The API adds nothing measurable, so
`fps::compose` and `fps::compositional_inverse` keep those ratios. Backend PR #163 (pruned
transforms, one-dimensional levels; open) reports 1.02 / 1.04 / 1.09 and 1.12 / 1.14 / 1.21; its
API is the same, so it reaches the frontend with no change here.
