## What the start does

- Not one rule. small's 25-instruction `umlal` loop is fast only at 0 mod 32 (#197). chirp's old
  59-instruction loop only at 4 (12 and 20: +5.8%, the other five +11.7%); its new 57-instruction
  loop only at 12 (every other start +5.3-5.9%, at 0-60 mod 64; 12 and 44 mod 64 alike, so mod 32
  is the period). multiply_chirp's 80-instruction loop is slower at 4 only (+4%). factor's old
  18-instruction loop: 3% slower at 0 than at 12, 10% at one more start; its new 17-instruction loop
  within 0.4% at every start. The recurrence's 10-instruction inner loop: 8% slower at 28 (it then
  spans 3 blocks of 32 bytes), equal elsewhere. The fast start is a property of the instructions:
  measure each loop after changing it.
- With `-mcpu=neoverse-v2` (`-falign-loops=32:16`) a loop starts at 0, 4, 8, 12 or 16 mod 32: GCC
  pads 20-28 to the next boundary, when it aligns the loop at all (not an inner loop entered as
  often as it turns, like the recurrence's).
- Short streams (lanewise `add`, `sub`, `neg`, `scale`; 8-11 instructions, 1-2 cycles per vector):
  1.0-1.6x by start, a different pattern for each op, size (L1 or L2) and surrounding code (the same
  9 instructions favour 0 mod 32 in the frontend's binary and 24 in a driver of their own;
  `shift*.cpp`, `out/lc-arm/shift-*`), and unrolled by 2 or 4 they still spread 1.2-1.35x. Not
  4K aliasing (arrays 32 bytes or 2 KiB apart mod 4 KiB: the same pattern). Not pinned: no start
  is good for all of them. Multiply-bound streams (scale, the Barrett product): within 1-2%.
- Guess, not measured further: the start sets how the loop's instructions fall into the front
  end's 32-byte fetch blocks, and with it how they are grouped at dispatch and steered to the two
  vector multiply pipes; loops near that limit lose 1-2 cycles per iteration.

## `simd::align_loop<k>(x...)` (align.hpp)

`.p2align 5` and k nops in an `asm volatile`, the loop's registers as in-out operands, right before
a do-while; nothing on other targets. GCC computes the operands before it, but may put other
setup (constants, derived pointers) between it and the loop: a fixed count for given code and
compiler, so k is chosen from the objdump and a scan, checked with both compilers. Used by factor
(rows loop, k = 0), chirp (pass: chirp k = 1, multiply_chirp k = 0) and the frontend's division
recurrence (k = 2). Every pinned loop is new code on Neon only (`__aarch64__`); x86 code and
binaries are unchanged.

## Not done, for later

- The element-wise streams: no pin helps (above). A faster form (4 vectors a step: best 240 against
  287 ns at 2048 words, 1967 against 2606 at 16384) still spreads by start.
- `multiply/16x16` (f * g on small): 9% by placement, one fast start; may explain #231's 7 ns.
- bostan_mori `coefficient/2`, the monomial division at 2^18-2^22: one slow start each in a single
  round, not confirmed.
- With `-falign-loops=32` in the user's flags GCC pads the pinned loops to 0 mod 32 again (chirp's
  then runs 5% slower than pinned, still faster than main's).
