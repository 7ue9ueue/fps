# #230 r1: pass's main loop at a measured address on arm

2026-10-16, claude, branch `agent/arm-align-r1-230`. `lc-arm` (Neoverse V2), `-O2 -mcpu=neoverse-v2`,
GCC 16.2.0 unless named. The survey of all units and the method: `backend/simd/notes/230-r1.md`.
Files: `~/Documents/hpc_library-explore/arm-align/issue230/` (`out/lc-arm/`).

## Finding

The sweep (`-falign-loops=32` against the default build) saw nothing in chirp: main's chirp loop
(`pass<false>`, K = 4: 4 Montgomery and 4 Shoup products per 16 words, 59 instructions) sits at 16
mod 32, and 0 is as slow. The placement scan (every function moved 0-28 bytes) shows it: only a
start at 4 mod 32 is fast; 12 and 20 cost 5.8%, the five others 11.7%, at every size from 2^10 on
(`chirp/<lg>`; `pscan-pass1.txt`). multiply_chirp's loop (`pass<true>`, 82 instructions): 4% slower
at one start only. About 2 cycles of 17 per step: the loop is bound by the 28 vector multiplies
per step on two pipes (14 cycles); guess, the start changes how they are grouped and steered.

## Change

arm, Neon only: pass's main loop on pointers, a do-while after `simd::align_loop`
(`backend/simd/align.hpp`); empty asm statements put the state vectors (x, g, step and its
quotient) in registers before the padding. GCC 15.2 and 16.2 still put 10 instructions (vector
constants, the SVE predicate) between the padding and chirp's loop, none before multiply_chirp's
(objdump of the chirp and frontend binaries, both compilers). The loop is new (57 instructions
for chirp, 80 for multiply_chirp with 16.2, 88 with 15.2), so its fast start was measured again:
0-15 nops after `.p2align 6` (`kscan-chirp6-16.2`, 3 interleaved runs, chirp/12, 16, 20):

- chirp: fast only at 12 mod 32 (12 and 44 mod 64 alike); every other start of 0-60 mod 64 +5.3-5.9%.
  kChirpLoopNops = 1 puts it there (with the 10 instructions in between), 15.2 and 16.2.
- multiply_chirp: +4% at 4 mod 32, equal elsewhere and to main. kMultiplyLoopNops = 0: at 0 mod 32,
  both compilers.

Other targets: the old loop (bench binaries byte-identical to main's, x86).

## Speed

`kernel.py bench chirp --target arm --base 0097fc0`, 7 rounds: geomean 0.9758. chirp/<lg> from 2^13
on 0.894-0.900 (chirp/20 0.8941, IQR 0.8939-0.8946; chirp/22 0.8944), chirp/10 0.933, chirp/8 0.969;
multiply_chirp 0.998-1.003 from 2^8 on; evaluate_geometric 0.992-0.998 (it runs chirp); the rest
within 0.3%. Slower: multiply_chirp/6 1.0071, chirp/6 1.0054, multiply_chirp/7 1.0054 (64-128
words, 150-190 ns: the padding and the register moves before the loop, about 1 ns a call). GCC 15.2
on both sides, 5 rounds: 0.9752, chirp/20 0.8941 (IQR 0.8933-0.8945). Against 98f2e85 the day
before: 0.9758 and 0.9753. The same code with `-falign-loops=32`
(`--base . --cxxflags`): 1.0133, chirp/14-22 1.057-1.059: GCC pads the pinned loop to 0 mod 32
again, a slow start; no faster, as the issue asks.
