# backend/factorials

Tables fact[i] = i! and inverse[i] = 1 / i! modulo a prime P (2^12 < P < 2^30), i < n <= P,
written into the caller's spans (`factorials.hpp`, API at the top). `select.hpp` lists the
variants per target (candidates: simd struct, vectors per chain, chain product, stores) and
reads the variant per size class from a tuned table (`tune::Table`, issue #54): compiled defaults in
`tuned.hpp` (generated by `tools/tune.py factorials` from `tuned.json`, measured by `tune.cpp`),
measured at run time by `tune.hpp` (the choice "factorials.variant"). `model.hpp` is the scalar
loop (the frontend's before this kernel), a variant like the others, and the tests' reference;
`transpose.hpp` holds the in-register lane moves per vector type (transposes, lane shifts) and
the non-temporal store;
`prefault.hpp` maps fresh output pages in one system call (issue #70 round 2). The frontend's
`Factorials` calls `tables` (issue #33).

## Design

`Chains<S, K, P, step>`: W = K S::lanes lanes, lane s covers positions [a_s, a_s + C). From
lc-opt's product chains (`lib/poly/factorials.hpp`: `Chain`, `scan`, `scan_chunk`), rewritten on
`simd` and `modarith` so one source runs on every target.

- Lanes inside the tables: a_s = min(h + s C, n - C). The lanes past n - C all cover the last C
  positions (the same values, stored twice). So no lane reads a multiplier past n or writes past
  n: no scratch buffer and copy (the prototype's `factorials()` wrote 64 C words to scratch and
  copied n of each table), and no n + 1024 <= P limit (lc-opt's). Any n >= 4 S::lanes up to P.
- Lanes aligned to fact (round 2): h < S::lanes is the words from fact to its next vector
  boundary, so every store of the lanes s < k = (n - h) / C into fact is aligned, and into
  inverse when it has fact's offset (two std::vectors of the same size do). Positions below h
  come from constant tables of i! and 1 / i!, i < 16; h! starts lane 0.
- C = chunk(n): n / W rounded up to the vector length; from 64 on, a multiple of 16, and one more
  line (16 words) when m = C / 16 is a multiple of 512 / W (round 3). The W lanes start m lines
  apart, so in a 64-set L1 they fall into 64 / gcd(m, 64) sets; the bump keeps it to at most 4
  streams per set. lc-opt's `scan_chunk` bumped every even m, which at powers of two costs
  16 W positions of duplicate work: 25% at n = 2^10 with 16 lanes. Never bumping is far worse
  where m is a large power of two (Log).
- Pass 1, lane products (a_s, a_s + C - 1], four factors per step (round 2): the first
  r = (C - 1) % 4 factors one by one, then x <- montgomery(x, g) with g = w (w + 1)(w + 2)(w + 3)
  in Montgomery form, w = a + r + 1 + 4j. g moves by its forward differences d1, d2, d3 (four
  modular adds per step; d4 = 4! 4^4 is constant). The start values come from vector products:
  G = z (z + 2) with z = w (w + 3), z(w + 4) = z(w) + 8w + 28, so G at w, w + 4, w + 8, w + 12 is
  5 Montgomery products per vector. Round 1 took two factors per step, lc-opt one. Lane k - 1
  also gives the product up to n - C (whole steps, then up to 3 scalar factors for that lane
  only): the start of the lanes past it. From 16 steps on and for K <= 2, two accumulators take
  the steps in turn, halving the product chain (round 3). The lane starts and the multipliers'
  bases are vector ops (round 3; before, two scalar `% P` per lane: 31-67 ns of setup).
- Pass 2, `starts` (round 3): first[s] = (a_s)! and 1 / last[s] = 1 / (a_s + C - 1)! in vector
  registers. first is an exclusive prefix product over the lanes of g_s = (a_s + 1) ... (a_(s+1))
  = product[s] (a_s + C) (h! shifted in at lane 0; the factor up to n - C at lane k - 1; 1 past
  it), and 1 / last[s] = 1 / last[k - 1] times an exclusive suffix product of r_t = a_t
  product[t] (lane t's own positions). Both in Montgomery form, log2(S::lanes) shifted products
  within a vector (valignd, palignr, ext; Avx2 vpermd and a blend) and log2(K) across vectors.
  One scalar inversion of last[k - 1] last[k] (the lanes past n - C all end at n - 1), by a
  branch-free binary extended Euclid (38-51 ns); two products split it. Before: k / 4 + 4
  dependent scalar `% P` products, ~4 k in all, then x^(P - 2) for all W lanes in vectors
  (150-230 ns: 30 steps of 4 contended vector products).
- Pass 3, the scan: an up chain from (a_s)! times a_s + 1, a_s + 2, ... and a down chain from
  1 / (a_s + C - 1)! times a_s + C - 1, a_s + C - 2, .... x < 2P. Two chain products (`Step`):
  - montgomery: the multiplier in Montgomery form, m = base + u, u = j 2^32 mod P shared by all
    lanes (the down chain uses base + P - u). x holds the plain product.
  - shoup (round 3): x m - floor(x q / 2^32) P with m plain, m = base + j, and
    q = floor(base 2^32 / P) + floor(j 2^32 / P) (down: base - j, the difference of the two minus
    1). The sum of two floors is floor(m 2^32 / P) or one less; with x < 2^31 the result is still
    in [0, 2P). floor(j 2^32 / P) = -(j 2^32 mod P) P^-1 mod 2^32: one mul_lo per step for all
    lanes. Per chain vector and step: mul_lo, mulhi, mul_sub and 2 adds; on Neon with SVE2 one
    umulh, mul, mls (Montgomery: 2 mul, 2 umulh), on x86 4 multiplies instead of 6.
  Every S::lanes steps the chains' records form a block; an S::lanes x S::lanes transpose turns
  it into vectors of consecutive positions, reduced below P and stored. The chains of the next
  block are interleaved with the transposes and stores of the current one (lc-opt's order); the
  last block is stored without running the chains past the end.
- Prefetch (issue #70): a variant with `prefetch` (`Chains<..., true>`) also prefetches, per
  lane, stream and block, the line after the one it stores (`__builtin_prefetch(p, 0, 3)`:
  prefetcht0), clamped to the lane's range. 32 lanes write 64 streams (up and down chains), more
  than Emerald Rapids' L2 hardware prefetcher follows: without it zmm K = 2's RFOs miss L2 (96%)
  and the store buffer fills (41% of cycles), 0.58-0.70 ns per position from about 2^19 on
  against 0.39-0.42 with it. It costs 1-8% where the tables fit in L2 (Log), so it is a variant
  property the table picks per class, not always on. A variant without it compiles from the same
  source as before (the prefetching loop is a separate `if constexpr` branch).
- Prefault (issue #70 round 2): from n = 2^17 (`kPrefaultSize`), `tables` first calls `prefault`
  (`prefault.hpp`, Linux) on fact, and on inverse if fact was fresh. If a word on the table's last
  whole page reads 0 and the page before it is not resident (mincore; the read maps the shared
  zero page on a fresh page, which then counts as resident), one madvise(MADV_POPULATE_WRITE) maps
  all its whole pages, zero-filled, as the writes would. Fresh tables (Factorials allocates two
  unwritten arrays; glibc maps them anew, or trims and regrows its heap, from about 128 KiB) took a
  page fault per 4 KiB: 70-80% of a call from 2^18 on, and in a VM a fault's entry and exit cost
  more than the batched work. Prefaulted, fresh tables cost 16-36% less (Log). A nonzero word
  means the table holds data, so it is resident: one load, no system call. A warm table of zeros
  costs one mincore, 1.5-4 us between kernel calls. -DFPS_NO_PREFAULT turns it off; `run_variant`
  and `Chains::run` never prefault.
- Stream (issue #70 round 3): a variant with `Store::stream` (`Streaming<S, K, step>`; zmm only)
  stores the lanes s < W - 1 with non-temporal stores (`_mm512_stream_si512`, then an sfence),
  from n = 2^22 (`kStreamSize`) and when inverse has fact's offset mod 64 bytes; otherwise it runs
  the plain variant (`Chains<S, K, P, step>::run`, the same function). From 2^22 on, C > 48 W + 15
  so k >= W - 1: lanes s < W - 1 start on the vector grid; the last lane, which may start at
  n - C, stores plain over positions lane W - 2 also writes (same values, any order). On Zen 5 the
  scan of 16 lanes runs at 0.25-0.26 ns per position from 2^17 on with it, 0.29-0.34 without
  (Log): plain stores to lines outside L2 stall it, prefetching does not help. Streamed tables are
  not cached afterwards, which costs their reader where plain stores would have left them in L3;
  from 2^22 (32 MiB, Zen 5's L3) that cost is 0-2.4% of a read pass, below it up to 3x (Log). So
  below 2^22 the variant stores plain, and the tuner times it only for classes that reach 2^22
  (`kStreams`, tune.hpp). Emerald Rapids does not gain (zmm K = 2 0.42 streamed against 0.43
  prefetched warm, 1.44 against 1.24 fresh): no streaming candidate on `avx512`.
- Code: `[[gnu::flatten]]` on each pass and `unrolled<N>` (index sequences) keep every lambda
  and modarith call inline and every block index constant. Without them GCC 15 kept the scan's
  lambdas as calls and the transposes as loops over stack arrays: scan 0.83-0.86 ns per position
  against 0.53-0.65 (`lc-bench`, avx2, K = 2 and 4). Lane moves are per-ISA intrinsics, not
  `S::permute`: GCC built Neon's `tbl` index tables at run time on every call (round 3, Log).
- Selection (issue #54 round 2; before: round 3's tiers, Log): a tuned choice per size class.
  - Classes: quarter octaves (e, e + 2^(k-2)], e = 2^k (1 + q / 4), from 16 to 2^26 (88; the
    last also takes larger n); below 17 the loop. A variant's lanes cover W C(n) >= n
    positions, a step function of n with steps on multiples of its lane grid (C rounds up to
    the vector length, then to 16): a class ends at a round size, a best case for every
    variant, and starts just past one, where wide variants pay the most slack.
  - Candidates per target (`select.hpp`; index 0 is the loop): `avx512` and `zen5` Sse.1.shoup,
    Avx512Vl.1 shoup and montgomery, Avx512Vl.2.mont, Avx512 (zmm) K = 1 both products, zmm
    K = 2 Montgomery with and without prefetch and Shoup with it (issue #70: without prefetch
    zmm K = 2 Shoup won only one class, by noise; `zen5` since round 2, Log), and for `zen5` zmm
    K = 1 Shoup streaming (round 3; zmm K = 2 Shoup streaming was 1-3% apart, either way by run,
    and its plain twin, which it runs below 2^22, is worse there than zmm K = 1's); `avx2` Sse.1.shoup,
    Avx2 K = 1 and 2, both products; `arm`
    Neon K = 1, 2, 4, both products;
    `sse` Sse K = 1, 2, both; `scalar` Scalar K = 2, 4, both. From a sweep of 7-12 variants at
    4 sizes per class on each machine (Log): a variant is kept if it wins somewhere on our
    machines or on another CPU running the build (Montgomery for ymm on Emerald Rapids, Neon
    Montgomery on the Apple M4).
  - `tables` reads `variants.get()[size_class(n)]` once per call and runs the variant
    (`run_variant`: a chain of compares on the index, no function pointers). `tuned.hpp` records
    a hash of each target's candidate list; a table for another list does not compile.

## Tests

`test.cpp`: the model against the definition (fact[i] = fact[i - 1] i, fact[i] inverse[i] = 1);
then `Chains` on every simd struct the machine can run, K = 1 (round 3), 2, 4, 8, both chain
products, and the selected `tables`, against the model: every n from 4 S::lanes up to 1100,
2^k - 1, 2^k, 2^k + 1 up to 2^20, both sides of every change of C up to 2^14 (so every count of
collapsed lanes), 20 random n, n = P - 1 and P for P = 4099 and 65537 (where the last multiplier is
P = 0 mod P), and P = 1073741789 (the largest prime below 2^30). Guard words after n must stay
untouched. Mutations caught: a lane start one lower, the wrong factor for the collapsed lanes, a
chain stopped a block early, the down chain's base off by one, the down chain's Shoup quotient
without its - 1 (round 3). Placements (round 2): on fewer sizes (every n up to 300, both sides of
each change of C up to 2^12, powers of two and neighbours from 2^9 to 2^17, 8 random n), K = 2,
tables at word offsets (1, 1), (4, 4), (12, 12), (15, 15), (0, 8), (3, 13), (9, 2) from a 64-byte
boundary, so every h and both equal and different offsets; words before the tables must stay
untouched too. The prefetching scan (issue #70), 32 lanes (zmm K = 2 both products; Sse K = 8,
Avx2 and Avx512Vl K = 4, Neon K = 8 Shoup in the -O2 build): 2^k - 1, 2^k, 2^k + 1 for k = 18 to
22 (to 19 in the sanitizer build, 20 for the narrower structs) at those offsets and (0, 0).
Streaming (round 3, Avx512): zmm K = 1 and 2 Shoup and K = 1 Montgomery with `Store::stream` at
the same sizes to 2^22 in both builds (so 2^22 and 2^22 + 1 stream, with every offset pair; the
different ones run plain), and below 2^22 as `chains` and `placements` (the plain path).
The selected `tables` also on both sides of every class where the compiled table
changes variant (to 2^22) and at 5 2^20 + 17. Every candidate of `select.hpp` as `Chains`
(K = 1 Montgomery and Scalar K = 2 Montgomery are not in the loops above) to 2^18 (2^14 in the
sanitizer build), and through `tables` with the table set to that candidate wherever it runs:
both sides of every class boundary to 2^13, 0, 1, 2, 16, 2^16 + 1, 2^18 - 1 (issue #54). Then
the size classes (each class ends where the next starts; points inside), and `tune.hpp`:
measure() at a small budget gives a valid table, keeps start above 2^sparse_lg without a sparse
part, gives each class its octave's fastest variant in the sparse part, keeps start everywhere
with a huge margin; the wisdom text reads back; parse refuses another list's hash, one value too
many or too few, a variant that does not exist and one below its least n; the table goes
through `tune::save` / `load`. Fresh tables (issue #70 round 2): each table in its own anonymous
mapping, never written, between guard pages, n = 2^17 - 1, 2^17, 2^17 + 5, 3 2^17 + 1, 2^20 + 3,
at word offsets 0, 5 and a page - 3, with fact, inverse, both or neither fresh, through `tables`
against the model, guard words untouched; then `prefault` alone: on fresh memory it populates
(Linux; every whole page resident after, still zero), not on resident memory, not without a whole
page, not when the first word is nonzero. `test_no_tuner.cpp`: with `-DFPS_NO_TUNER` the table is the
constexpr defaults and `tables` matches the model. The ASan/UBSan build (5x the -O2 build's compile time) runs a
subset since round 3: K = 1, 2, 4, both chain products, P = 998244353, 4099 and 1073741789, sizes
to 2^20 for K = 2 Shoup and 2^16 for the rest (`lc-zen5-test`: 100 s to build against 257 s for
all of it; main's test 152 s). Passes at -O2 and ASan/UBSan on `lc-amd` (scalar, sse, avx2),
`lc-intel-test` (avx512), `lc-zen5-test`, `lc-arm` and the Mac (scalar, arm). The frontend's `test_factorials.cpp` runs the kernel through
`Factorials` and through `detail::factorial_tables` for every n <= 4099 at P = 4099.

## Sources

- lc-opt `lib/poly/factorials.hpp` and its notes (Factorials): the product chains, the scan with
  in-register 8 x 8 transposes, `scan_chunk`. Moved and rewritten here.
- Montgomery multiplication: modarith (P. Montgomery, Math. Comp. 44, 1985).
- Finite differences for the pair (round 1) and quad (round 2) products: the standard
  forward-difference table of a polynomial; no source used.
- Shoup multiplication (round 3, the scan's chains): modarith (V. Shoup, NTL; D. Harvey, J. Symb.
  Comp. 60, 2014). The stepped quotient (a sum of two floors, one short at most) is ours.
- madvise(MADV_POPULATE_WRITE) and mincore (issue #70 round 2): the Linux man pages.
- Non-temporal stores and sfence (round 3): Intel's instruction set reference (`movntdq`,
  `sfence`); IFMA (`vpmadd52luq`, `vpmadd52huq`): the same.
- Binary extended Euclid (round 3, the inversion): J. Stein's binary GCD; the halvings deferred
  to the other coefficient as doublings: the idea of T. Pornin, "Optimized Binary GCD for Modular
  Inversion" (IACR ePrint 2020/972); no code used.
