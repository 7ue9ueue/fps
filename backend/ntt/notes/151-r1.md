# #151 r1: generated Neon asm for Neoverse V2 (variant neon)

2026-10-13, claude (issue #151, round 1, target arm). A generator of NTT butterfly kernels for
Neoverse V2 (`gen_neon_kernels.py` -> `neon_kernels.hpp`) and the variant `neon` (`neon.hpp`):
`intrinsics<Neon>` with the generated kernels for the product bottoms, the group levels and the
transform bottoms. Base: main 877a450. `lc-arm` (Google Axion, Neoverse V2, 2.97 GHz), GCC 15.2 in
the pinned image, `-O2 -mcpu=neoverse-v2`. Exploration (probes, variant harnesses, raw output):
`~/Documents/hpc_library-explore/ntt/arm-r1/` (`micro.cpp`, `multi.py`/`multi.cpp`,
`multiloop.py`/`multiloop.cpp`, `indep.py`, `pstat.sh`, `record.sh`; `x151/` in the round's tree).

## Design

- Generator (lc-opt's `lib/ntt/gen_kernels.py` and this repo's `gen_avx2_*.py` are the model):
  dataflow graph of Neon ops plus SVE2 `umulh` (unpredicated, 128-bit vectors on V2) -> source
  order -> list schedule on a V2 model (`M` multiplies on V0/V2, latency 4, accumulators 1; `A` any
  pipe, latency 2; stores a V0/V1 data uop; loads 3 a cycle) -> `repattern` (vector ops reordered
  to alternate M, A where the dependences allow) -> linear-scan allocation onto v0-v28 (v29-v31: P,
  2P, -P^-1) -> one asm statement.
- Register budget without deadlock: the scheduler takes an op that grows the live set only if the
  remaining ops can still follow in source order within the budget (`Liveness.feasible`, an O(n)
  walk). The first scheduler (lc-opt's rule: an op waits while it would exceed the budget, plus
  windows and margins) deadlocked on most knob settings of these graphs.
- Twiddles by element: `mul v, x, w.s[i]` and `umlal v, x, b.s[i]` cost what the vector forms cost
  (probe), so twiddle values are lanes of loaded vectors and B's coefficients lanes of B (no `ld1r`
  or `dup` per b_i: GCC's code had 32 `dup` per group); only the Shoup quotients are broadcast
  (`dup`, as SVE2 `umulh` has no indexed form): 3 per group.
- Product bottom (`bottom_first/last/both`, square and stored forms): two groups per statement;
  `both` = the products and inverse of pair j interleaved (proportionally) with the forward half of
  pair j + 1, which balances the multiply-heavy and add-heavy halves (pair: 496 M, 476 A, 208 L,
  64 S). Leaf windows through a stack buffer (rows [w_t A_t, A_t], 16 stores and 48 `ldur` per
  group); t = 1, 3 store P - canonical(y A) (lc-opt's trick: no second quotient). The products run
  column by column, reloading windows and B for each column (loads are cheap, registers are not).
- Group loops: one asm loop per group, 4 columns per iteration, twiddles in v24-v28, pointers
  advanced at the end of each iteration; in place (inputs < 4P) and from a source (inputs < 2P:
  the first level of a subtree after the radix-2 level, reading the caller's or the shared half).
- Transform bottoms: two groups per statement, a C++ loop over pairs.
- Not generated (intrinsics, as before): bottoms of single groups (subtrees of 4 leaves: 2^6 and
  2^7), `inverse_group_scaled`, `inverse_terms`, radix-2 and radix-4 tops, partial first levels.

## Attempts

1. Leaf windows in registers (`ext` from the row vectors, B kept in registers, the whole chain of a
   pair in one statement): the source order needs 35-40 live values (A, B and rows of both groups),
   above the 29 registers; abandoned before timing.
2. Buffered pairs, forward half of pair j + 1 with products of pair j: first version 7815 -> 5867
   cycles (0.75). Leaf buffer stores and loads cost nothing measurable: with the forward half
   writing a dummy buffer (wrong results) 5680 against 5684.
3. Scheduler knobs, 37 + 25 variants of `bottom_both` in one binary (`multi.cpp`; window 48-None,
   margin 0/8, age 0/0.1/0.2, latency_scale 0.25-1, merge shift -0.1..0.1): 5520-6360 cycles; the
   M/A pattern gained 2-5% in every configuration; the best five within 2% (run-to-run spread about
   2%). Kept: window 160 + pattern.
4. The same instruction stream with every register dependence removed (`indep.py`): 4801 cycles
   (one run 8016, bimodal: garbage store data to the same addresses). So the pipes and their
   steering allow about 4800 for this stream; the dependences cost the rest (5520-5690).
5. Group loops, 16 variants (`multiloop.cpp`, quarters of 256 words): 4 columns per iteration 606
   (forward) / 639 (inverse) cycles against 735/725 for 2 and 678/694 for 8; no pattern 625/635;
   source order 868/814; MMAA as MA. Kept: 4 columns, pattern.
6. Steering (a guess, from the counters and the earlier `v2mix.cpp` patterns, period-2 and
   period-4 M/A orders 4.0 per cycle, period 3 3.0): the core picks pipes at dispatch; with A ops
   spread evenly over V0-V3 the bottom's V0/V2 load is M/2 + A/4 per pipe = 5872 cycles per 32
   groups, close to the first version's 5852. Not confirmed (no per-pipe PMU events on V2).
