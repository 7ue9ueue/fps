## What was built

- `Generated<Zmm>::kJoinBottoms` (avx512.hpp): at 2^6 and 2^7 every subtree under the top level is
  one group, and `intrinsics<S>` ran each bottom with `count = 1`, so `Leaf` (ymm, one group at a
  time) ran there and none of the pair kernels did. With the member, `Ntt::kJoin` (#151 r2's hook,
  unchanged) runs all subtrees' bottoms in one call: the generated product bottoms
  (`multiply_first/last/both`, `square_*`, `stored_*`), the transforms' bottom level
  (`bottom_forward2/4`, `bottom_inverse2/4` on Zen 5, `WideBottom` otherwise), WideBottom's
  `inverse_terms`.
- `Ntt::inverse_into` (intrinsics.hpp; the inverse into other memory and of the values form):
  its joined lengths (2^6, 2^7) dispatched at its top to `inverse_into_joined`, a function of its
  own, so its code for the other lengths is the code without joins (Layout, below). The only change
  to intrinsics.hpp; it reaches arm too (neon joins since #151 r2).
- Bottom level in statements of 2 and 4 pairs on Emerald Rapids too (round 150 tried one pair per
  statement only: 1.00-1.01 forward, 1.06-1.10 inverse): `bottom_forward2` (Emerald Rapids model,
  window 128), `bottom_forward4` (Zen 5 model, window 128: the Emerald Rapids scheduler, with no
  feasibility check, deadlocks on 4 pairs), `bottom_inverse4` (Zen 5 model, window 64);
  `Generated<Zmm>::bottom_forward` and `bottom_inverse` now on both targets (the inverse on Emerald
  Rapids: 4 pairs from a multiple of 8, any other run to `WideBottom` whole).
- Zen 5's 4-pair bottoms rescheduled with a window of 128 (round 152 tried none, 32, 64), and its
  2-pair forward on the Emerald Rapids model (`PAIR_KNOBS` in gen_avx512_kernels.py).
- `test_join.cpp` (new): every op that joins (transforms in place and in the values form,
  forward_upper and inverse_upper, inverses into other memory, Convolution products sparse and
  dense, products, squares and middle products from spans, forward from spans, forward_product,
  forward_upper from spans, cyclic products of both halves and negated, inverse_product of 1 to 3
  terms, forward_hooked and inverse_hooked) at 2^6, 2^7 and 2^8 against the scalar variant, word
  for word, on every variant and the tuned one, inputs random, all P - 1, zeros, mixed. Four
  mutations of the joins (forward's bottom from group 2, forward_upper's from group 0, the radix-4
  multiply's on 2 groups, inverse_hooked's stage on half the leaves) failed 6-15 checks each.
  `test_zen5.cpp`'s bottom tests (2 to 64 groups from first groups 0, 2, 6, 64, 1000, against
  `Ntt<Avx512>`) now run asm on the avx512 target too.

## Layout on Zen 5 (`x176/multi.sh`: each tree's bench built at code shifts 0 and 1024, round robin)

Every variant below executes the same kernels; what moves is code placement. Ratios against main
(7a20369 unless said), medians over shifts and rounds.

1. **Joins inlined in `inverse_into`** (the first build, as #151 r2 does it for neon):
   inverse_values/9 1.113-1.118 at shifts 0, 1024, 2048, 3072, at 16, 32, 48, 80, 144 bytes,
   with `-falign-functions=32/64/128` 1.112-1.116, with `-ffunction-sections
   -Wl,--sort-section=name` 1.108; inverse_to/9 1.00. Not alignment: inverse_into's own code for
   the other lengths changed with the inlined branch (the first agent's `syms.sh`, `bdiff.sh`: of
   the paths inverse_values/9 runs, only inverse_into's code differs with and without the member).
2. **Joined bottoms out of line** (`joined_bottom`, noinline, called where the inline join was):
   inverse_values/9 0.996-1.001. But fps::roots of degree 64 ran 1.14-1.15 (frontend, roots/6 and
   roots_split/6), in five runs. Bisect (same binaries otherwise, shifts 0 and 1024): main +
   `kJoinBottoms` alone 0.995, the round's kernels without the member 0.999, both 1.147; both with
   main's Zen 5 kernels 1.146; both with main's intrinsics.hpp (so variant 1) 1.005. The tracer
   (`trace.cpp`, one call single-stepped): roots/6 runs neither `inverse_into` nor `joined_bottom`;
   with and without the out-of-line function it executes the same 115602 instructions, 8385
   distinct, in the same functions. At shifts 0, 16, 32, 48, 64, 128, 256, 512 bytes: 1.15 at
   each. So the placement of code that never runs moved roots/6 by 15%, at every alignment (a
   guess: relative placement of roots' own hot functions, `pair_step` and the coset evaluations,
   against each other; no PMU on the Zen 5 VMs to say which structure).
3. **The joined lengths dispatched at the top of `inverse_into`** (`inverse_into_joined`, kept):
   inverse_values/9 0.997, /11 0.992, forward_values/11 0.965; roots/6 0.991, roots_split/6 0.991
   (one run of A = variant 1, B = this, C = variant 2 against main: inverse_values/9 1.118, 0.997,
   0.998; roots/6 0.994, 0.991, 1.144).
4. **Every join out of line** (the first agent's `out_of_line([=] { ... })` at each joined site):
   forward/11 1.138, inverse_values/6 1.174, /7 1.10, squares at 2^14-2^18 1.015-1.018 against the
   same tree without the member. Not kept.
5. **The products' joined lengths in functions of their own** (`multiply_joined`,
   `product_joined<kSquare>`, as 3; branch `x176-P`): squares at 2^16-2^20 1.012-1.019 (variant 3:
   1.017-1.022), square/10 1.040, /11 1.046 (1.001, 1.022), product/11 1.035, products and
   convolutions at 2^18-2^20 0.987-0.996 (0.995-1.001). Not kept: no better overall, more code.
6. **Squares at 2^14-2^22** run 1.0-2.2% slower than main in every build with the member
   (1.007-1.012 against the same tree without it, the first agent's `xbin7`), though a square at
   those lengths executes no joined code; with the squares' joins dispatched as in 3 (5) they stay
   1.2-1.9% slower. Reported as layout: products at 2^12-2^16 run 5.6-5.7K distinct
   instructions per call against Zen 5's op cache of about 5.9K (#152 r2), where placement
   decides the conflicts.
