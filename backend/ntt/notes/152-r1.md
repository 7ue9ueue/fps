## What was built

- `gen_avx512_kernels.py` writes two headers (`OUTPUTS`): `avx512_kernels.hpp` (Emerald Rapids,
  byte-identical to main's) and `zen5_kernels.hpp` (new). `use(target)` sets the model; for Zen 5
  the scheduler matches each cycle's uops to pipes (classes share pipes), counts a load across a
  line as two slots, and takes only ops after which the source order still fits the registers
  (`Liveness`, the rule of gen_neon_kernels.py, #151; with a window the reference order's next op
  is always a candidate). Without it the Zen 5 model deadlocked on the forward loop and every
  `multiply_both` (whose interleaved source order needs 28 registers, 27 free: `lean_order` gives
  a reference order that fits). Emerald Rapids keeps #150's scheduler (first free pipe, a load op
  counted twice, no feasibility) so its header does not change. New knobs: `model` (schedule one
  kernel on another target's model), `latency_scale`, `width`.
- New shapes: `bottom_forward`/`bottom_inverse` of 2 and 4 pairs per statement (twiddles at fixed
  offsets from those of the first pair: k a multiple of 4 or 8), `small_groups` (forward groups of
  two columns, quarters of 32 words, 4 groups per statement, group 0 as identity in `_first`),
  `multiply_first/last/both` of 2 pairs per stage (not emitted).
- `avx512.hpp`: on znver4/5 it includes `zen5_kernels.hpp`, and `Generated<Zmm>` adds the optional
  hooks of #151 (`inverse`, `bottom_forward`, `bottom_inverse`) and a new one, `forward_groups`
  (intrinsics.hpp, in `Butterflies::forward_groups`); `forward` takes group 0 too (identity loops
  for inputs < P, < 2P, < 4P). `select.hpp`: zen5's candidates = avx512's (the variant avx512
  added); `Native` is avx512 on zen5 (the leaf-form ops: values form, inverse into other memory).
- `machines.py` (Zen 5) and `probe.cpp`: the measured classes and memory forms (simd notes).

## Zen 5 model (probe.cpp, lc-zen5)

Mixed pairs, cycles per instruction: vpermd + vpsrlq 0.34, vpermd + vpmuludq 0.34, vpermd + vpaddd
0.25, vpermd + vpblendmd 0.25: the permutes' two pipes share one with the multiplies (FP0, FP3 in
the model) and one with the shifts (FP1, FP2), so 'FP0 FP1' (which pipes is a guess). Merge-masked
vpbroadcastd from memory: a permute-class uop (with vpermd 0.5, vpmuludq 0.35, vpsrlq 0.34).
vpblendmd, vpminud, vpaddd, vpsubd, vpmulld + vpaddd: 0.25 (any pipe). zmm loads 2 per cycle, one 4
bytes past a line boundary takes two slots (1.0), stores 1 per cycle with no vector uop (6 stores
in 42 vpaddd: 10.5 cycles; 48 vpaddd: 12), folded memory operands and `{1to16}` no vector uop.

Uop floors from the graphs (`count.py`; total uops / 4 decides on Zen 5, every class fits): forward
loop 11.25 cycles per column (measured 12.7, 89%), inverse 12 (12.7, 94%), forward identity 8
(8.5), inverse identity 7.5 (7.9); bottom forward 19.25 per pair (1 pair per statement 29.6, 65%);
product bottom 114 per pair (148, 77%).

## Open

- Code size on Zen 5: composite algorithms at 2^10-2^11 (evaluate, sqrt) lose 2-10% with the
  asm at short lengths, while each op alone gains. Fewer, smaller kernels (no `_first` two-column
  kernel, no 2-pair bottoms, one identity loop for every input bound) or a table that weighs
  code footprint; tune.cpp times each op hot and alone.
- The product bottom runs at 77% of its uop floor; the Emerald Rapids model schedules it better
  than the Zen 5 model, and bigger statements lose to code size in whole products.
- Inverse two-column groups: faster alone, slower inside products at 2^10 (not code layout).
- Not generated on Zen 5: the scaled inverse top groups (`inverse_group_scaled`, a level of every
  inverse and product), first levels from other memory (`forward_from`), radix-2 levels.
